# Playbook: парсинг Авито через агента (тестовый режим)

Режим: сбор первых данных без прокси, через браузерную сессию агента на российском резидентном IP.
Приоритеты: **достоверность данных > низкий риск блокировки > экономия токенов**. Скорость не важна.
Версия 2 (2026-10-03): добавлены уроки полного прохода шага 7,50–7,55 млн (155/156 карточек).

## 1. Правила (обязательные)

### 1.1. Доступ и блокировки
- Работать **только с российского IP без VPN**. Признак бана: заголовок страницы
  «Доступ ограничен: проблема с IP» (у curl — HTTP 429, 403, 439 + тот же текст в теле).
- **Блок засчитывать только по строгому признаку**: «Доступ ограничен» И отсутствие
  hydration-данных. Фраза может встретиться в теле обычной карточки (описание, похожие
  объявления) — это не блок; блок-страница hydration не содержит.
- При блоке **не ретраить тот же URL** — ни разу. Остановить сессию, сообщить пользователю.
  Возобновление — после снятия блока (капча решается пользователем вручную в браузере или
  кулдаун ≥30 мин). После снятия — сначала **пробная карточка**, потом основной прогон.
- Одна сессия = одна вкладка браузера, никакого параллелизма. Пауза **2,5–6 сек** между карточками.
- Реальный порог бана (замер 2026-10-02): **~110 загрузок страниц за ~40 минут → бан с капчей**.
  Лимит сессии: **≤ 80–100 карточек**; крупный шаг цены делить на 2 сессии.
- Не обновлять страницу повторно (`reload`) без необходимости — каждая загрузка = риск для IP.

### 1.2. URL: ничего не выдумывать
- Слаги категорий содержат хеши Авито, которые меняются. **Запрещено конструировать URL по
  образцу** — это даёт 404 «Такой страницы не существует».
- Правильный путь: открыть канонический адрес (`/{город}/kvartiry/prodam`) → применить фильтры
  через UI → дальше работать только с URL, которые вернул сам сайт.
- Фильтры в UI: клик по чекбоксу делать по label или координатам (`cua.click` по центру label) —
  сам `<input>` скрыт стилями и клик по нему вечно «висит». Перед кликами закрыть cookie-баннер.
- Цена кодируется в параметр `f=` (base64-JSON `{"from":...,"to":...}`); при установке обеих
  границ «от» иногда слетает — проверять обе подстроки в декодированном `f=`.
- **Истёкшие объявления**: 404 «Объявление истекло» при живом URL — не ошибка парсинга; пометить
  `expired` и пропустить, ретраи не нужны (гидрации там не будет никогда).

### 1.3. Извлечение данных — только hydration-JSON
- Единственный источник данных карточки: `window.__staticRouterHydrationData.loaderData["catalog-or-main-or-item"].buyerItem.item`.
  JSON встроен в `<script>` HTML — не ходить по DOM (классы хешированные и нестабильные).
- Из листинга: список `[data-marker="item"]` (title/price/url/address) — достаточно для списка URL.
- Из карточки брать из item: `title, id, url, price.price|formattedPrice, sortFormatedDate, geo.address,
  geo.coords{lat,lng}, geo.references (метро), houseParams.data.items (ЖК/дом), description (HTML→текст),
  imageUrls (4 размера), developerV2, seller.isRealtyDeveloper, breadcrumbs`.
- **Запрещено печатать DOM-снапшоты целиком** (снапшот выдачи ~200 000 символов = сожжённые токены).
- Медленная гидрация: после `goto` ждать появления hydration-объекта polling'ом (до 15 сек),
  а не фиксированную паузу.

### 1.4. Надёжность записи (вместо «печатай JSON в чат»)
- **Логика прогона — в файл-драйвер** (образец: `avito_run_7.5-7.55M_2026-10-02/docatka_driver.mjs`):
  агент вызывает `runBatch(browser, tab, n)`, в чат возвращаются только короткие статусы
  (`id ok 4812B` / `id fail причина`). Сами JSON (4–8 КБ на карточку) в контекст не попадают —
  экономия токенов на порядок.
- Каждая карточка пишется на диск **сразу после извлечения**: append одной строки в `cards.jsonl`.
  При старте драйвер лечит обрезанные строки (битые — в `.quarantine`).
- Атомарный state-файл прогресса (`docatka_state.json`: tmp + rename) — после любого сбоя прогон
  продолжается с места остановки; неудачи ретраятся 1 раз, при блоке — полный стоп.
- Двойная проверка перед записью: navVerify (после `goto` проверить
  `location.origin + location.pathname === целевой URL`, при несовпадении — `reload`, до 3 попыток;
  проглоченные ошибки `goto` оставляют hydration прошлой страницы!) + извлечённый `avito_id` ==
  id из ссылки. Dedupe везде по **avito_id**, не по строке URL (relative/absolute не совпадают).
- **Перед основным прогоном всегда пробная карточка** — на ней отлавливаются баги драйвера
  (в шаге 7,5М пробный прогон поймал 2 бага: регулярка id, ложная детекция блока) и актуальный блок.

### 1.5. Достоверность (валидация перед финализацией)
- Цену хранить числом. Префикс «от …» — цена застройщика от минимума, флаг `price_is_from: true`.
- Метро: валидно только при `time` и/или `line_color`; иначе это район — пометить `note`.
- Кросс-проверки: площадь в title == house_params; этаж в title == `Этаж: N из M`; цена в диапазоне
  фильтра. Расхождение → `warnings`, не молча исправлять.
- Незаполненные поля — `null`, ничего не домысливать. Не нормализовать перемешанные
  латин/кириллические символы в описаниях (антипарсинг Авито) — сохранять как есть.
- Финал: единый JSON (`meta` с датой/параметрами/аномалиями + `items[]` в порядке листинга),
  проверка валидности, сверка покрытия: `собрано/всего` + список отсутствующих id с причинами.

### 1.6. Фото
- Ссылки — `item.imageUrls`, качать размер 1280x960. CDN `img.avito.st` не требует кук/реферера —
  достаточно User-Agent. Фото качать **отдельно от основного прогона**, фоном — блок основного
  сайта на CDN не действует.
- Манифест TSV (`url → {avito_id}_{n}.jpg`) строить с дедупликацией против уже скачанных файлов.
- Скачка фоном — только через **скрипт-файл** (`dl_photos.sh`), не инлайн-nohup: quoting `$'\t'`
  в инлайне ломается молча (цикл «жив», но ничего не качает). Маркер `photos_download.done`
  удалять перед новым запуском — старый маркер врёт о готовности.
- Формат файла определять по магическим байтам (JPEG/WebP), расширение не гарантия.

## 2. Готовый промпт для следующего прогона

```text
Задача: спарсить объявления Авито по шагу цены {from}–{to} и сохранить структурированный JSON.

Параметры:
- Город: {city_slug}; фильтры: {текстом}; объявления: все по фильтру
- Каталог сессии: services/parser-service/internal/avito/testdata/avito_run_{range}_{дата}/

Порядок:
1. Проверь доступ пробной карточкой через драйвер (см. 1.4): если блок — СТОП, отчёт, не ретраи.
2. Собери URL выдачи через UI-фильтры (только URL от сайта), сохми urls.jsonl.
3. Прогони карточки драйвером батчами по 3 (паузы 2,5–6 сек, ≤100 карточек за сессию;
   крупный шаг — дели на 2 сессии). Каждая запись: navVerify + avito_id-сверка + мгновенный append.
   404 «Объявление истекло» = expired, пропустить.
4. Валидируй cards.jsonl (битые строки, dedupe по id), сверяй покрытие с urls.jsonl.
5. Собери итоговый JSON: meta + items[] (порядок листинга), проверь валидность.
6. Фото фоном через dl_photos.sh по манифесту с дедупликацией; маркер .done удалить до запуска.

Ограничения: без VPN; одна вкладка; при блоке — СТОП и отчёт; никаких ретраев заблокированного URL.
```

## 3. Чек-лист перед завершением сессии

- [ ] Пробная карточка была выполнена до основного прогона
- [ ] JSON валиден, схема едина, все `null` объяснимы; битых строк в JSONL нет
- [ ] Покрытие сверено с urls.jsonl; отсутствующие id имеют причину (expired/блок)
- [ ] В `meta` зафиксированы параметры выборки и все аномалии
- [ ] Нет в чате полных DOM-снапшотов и полных JSON карточек (только статусы)
- [ ] Ни одного ретрая заблокированного URL
- [ ] Фоновая скачка фото: маркер .done свежий, число файлов = числу в манифесте
